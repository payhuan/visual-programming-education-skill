# 图形化编程游戏地图设计规范

本规范适用于走迷宫、道路驾驶、寻路、巡游等依赖空间移动的关卡。用户指定地图风格或游戏规则时，优先遵循用户要求；无特别指定时按以下规则设计。地图美术、关卡规则和模拟器必须引用同一份拓扑数据，不能各自画一张看似相同但连接关系不同的地图。

## 1. 先定义拓扑，再绘图

在绘制地图前，定义可通行的网格或道路图：

- 记录起点、终点、坐标/节点、可通行连接、墙/不可达区域、危险格、路口、检查点、信号灯等实际会影响程序的对象。
- 对网格地图，明确格子坐标、角色朝向和四邻接移动规则；对道路地图，明确道路节点及其有向/无向连接。不得靠 SVG 路径或 CSS 装饰线推断可走关系。
- 地图绘制和模拟移动必须消费同一份权威邻接数据。若地图用显式 `edges`，移动也必须查询这些边；若用规则网格推导邻接，则渲染必须显示所有可移动的相邻连接。不能一边按线段/边列表绘图，另一边仅按坐标距离推断可走。
- “前进一步”只移动到当前朝向相邻的下一个格/路段；左转、右转只改变朝向。不得让一个移动指令直接跳到列表中的下一站或沿预设线路自动转弯，除非用户明确选择高层导航抽象。
- 地图上的障碍、陷阱、红绿灯、站点和目标必须绑定到拓扑节点/边，并真实影响执行状态和结果。纯装饰元素不应看起来像可交互危险或通路。

## 2. 地图必须服务学习目标

- 若教学目标包含前进、转向和路线规划，默认关卡地图至少应有两次方向改变和一个有意义的路线选择点；可通过障碍、不同长度/风险的通路或有教学目的的死路形成决策。不要用一条直线串起全部目标点。
- 仅在主路线旁添加不连通、不可进入或没有后果的短支线，不算有效分支。路线规划关卡至少有一个路口，其不同可行方向会通往不同的连通路径/目标，或产生明确且可观察的教学结果；单条必经链加装饰性岔口不算路径选择。
- 如果关卡只教顺序执行，或用户明确要求线性路线，可以采用简单路线，但仍须如实说明这是教学选择，不能声称在训练转向/寻路。
- 分支必须是真实可达的连接选择，不是画出的岔路实际仍被代码强制传送回固定路线。危险/信号灯可以按学习目标逐关引入，不为增加视觉复杂度而塞入无关障碍。
- 对多个目标点/企业站点，使用弯折或有支路的连通路网安排点位；若要求按顺序讲解，程序仍需逐段移动并可观察经过的路线，不能凭“下一站”积木瞬间跳点。
- 用图形化编程教学时，关卡挑战必须允许学生实际组装并运行与本关概念对应的积木；多选题可作为辅助手段，不能代替程序挑战。
- 难度通过格数、岔路数、障碍布局、条件要求和路线效率逐步提高；地图形状本身不能制造不可见或不可解的谜题。

## 3. 地图视觉约定

- 清楚区分起点、终点、可走区域、墙/边界、路口、危险、信号灯、目标点和角色当前位置；提供图例或就地标签，避免仅靠颜色编码。
- 可走通路须连续可追踪；相邻关系与路口几何视觉一致。转弯、死路和交叉口需能一眼区分，路线或路径高亮不得遮挡障碍与目标。
- 角色的位置和朝向都应可见，尤其当“前进一步”依赖当前朝向时。执行动画结束后角色必须落在拓扑模型对应的位置。
- 小屏幕上地图可缩放或平移；缩放不得改变点击/拖拽坐标和格子判定。

## 4. 连通性和路线校验

- 在关卡交付前，从地图数据运行可达性检查，确认起点能到达所有必需目标，并确认终点/顺序约束有可行解。
- 为教学意图列出至少一条参考路线（坐标/节点和每步朝向），用原子积木模拟执行，确认它确实可通关。
- 对要求学生选择路线的关卡，验证至少存在一个真实分支和一个有意义的错误选择/死路；若有多个有效路径，不应只接受唯一节点序列。
- 遍历地图上每条绘制连接和每个可执行移动边，确认二者完全一致；尝试从分支向前移动、转弯和返回，确保没有只在画面出现或只在代码存在的道路。
- 分别验证撞墙、进入陷阱、遇红灯未等待、到达终点、过早停止和重复前进等相关结果；地图显示、转移表和执行器结果必须一致。
