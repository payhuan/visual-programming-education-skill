# 图形化编程游戏状态转移规范

本规范要求把程序运行、世界状态和指令控制流写成显式规则。变量名和数据结构由项目决定，但每条指令的前提、状态变化、程序计数器变化、时间效果及结束结果都必须明确，且 UI、模拟器与反馈使用同一状态来源。

## 1. 定义状态

实现前列出本游戏确实需要的状态，不要让关键状态只存在于 DOM 样式或动画中。通常分为：

- **世界状态**：位置、朝向、速度、地图/路线、障碍/陷阱、信号灯、目标和收集物等。
- **执行状态**：`idle`、`running`、`waiting`、`succeeded`、`failed`、`stopped`、`timed_out` 等适用阶段。
- **控制流状态**：当前语句/程序计数器、嵌套循环计数、条件分支位置、正在等待的条件。
- **计时状态**：已用时间、时间上限、当前指令消耗的时间；只有实际需要计时的玩法才加入。
- **进度状态**：已选择、已学习、已解锁、已安装、已完成等由用户需求决定的状态。

为每个状态写明初始值、可写入它的指令/事件、重置行为，以及其影响的可见元素。相同概念只能有一个权威状态值；不要出现显示为“绿灯”而执行器仍判断为“红灯”之类的双份状态。

## 2. 为每条指令定义转移

在实现前为每种积木建立转移表。至少包含：

| 字段 | 要回答的问题 |
|---|---|
| 前置状态/守卫 | 指令何时可执行？若不满足，阻塞、等待、失败还是忽略？ |
| 原子效果 | 本次执行实际改了什么状态？是否移动、转向、调速或只读取条件？ |
| 程序计数器/控制流 | 成功后进入哪条指令、哪个分支或哪个循环位置？ |
| 时间效果 | 是否消耗时间，如何受速度/等待/超时影响？ |
| 终止与反馈 | 何时成功、失败、停止或超时？学生能看到什么原因？ |

一个基本执行循环应按明确顺序完成：取当前指令 → 检查执行前提 → 执行一次原子效果或进入等待/分支 → 更新权威状态 → 按规则检查碰撞、危险、目标和超时 → 如仍在运行则更新程序计数器 → 渲染新状态并执行下一步。每步只执行一次，不允许动画先改变视觉位置而状态稍后才补写。

## 3. 默认控制流规则

- **普通语句**：前置条件满足且效果成功后，程序计数器才前进到下一条。前置条件失败时按转移表规定的失败/阻塞行为处理，不得仍然假装成功推进。
- **转向**：左转/右转只改变朝向，不改变位置；执行成功后进入下一条。需要在路口才能转向的游戏，应明确检测路口的时机和非法转向结果，不能暗中自动选路。
- **移动**：先根据当前空间模型计算目标位置/轨迹，再检查边界、墙、陷阱等。格网模型按明确格长更新位置；连续恒速模型按 `位移 = 速度 × 持续时间` 计算，单位换算明确，并在接触碰撞体时按规则停止/失败。不得用无单位的“步”或“站”作为连续空间位移量。被阻挡时是否原地停止、失败或触发惩罚须固定并反馈。
- **条件**：先读取当前权威状态，再只进入一个明确分支；条件检查本身不移动角色。`else` 分支和空分支的行为必须定义。
- **循环**：进入循环时初始化计数/条件状态；每轮执行其内部语句栈；完成后判断继续或退出并跳转到明确位置。循环嵌套时各自维护状态，并设置总步数上限。
- **等待**：条件未满足时执行状态为 `waiting`，程序计数器留在当前等待指令；条件满足时才恢复并前进。超时、停止、重置和条件反复变化的行为都须定义。
- **停止**：明确停止是结束程序、使角色停住还是二者兼有。提前停止不得自动判定为抵达终点；若目的地本身要求“停车”，把停车条件写入目标判定。

## 4. 目标、危险和冲突判定

- 明确何时检查成功条件：默认在初始化时检查一次，并在每次成功的世界状态变化后、执行下一条指令前再检查。若玩法要求其他时机，需在关卡规则中说明。
- 明确目标条件是只看位置，还是还要求朝向、收集物、速度、讲解完成等组合状态；使用显式条件，不靠画面接近终点推断成功。
- 明确进入同一格/路段同时满足多个条件时的优先级。通用默认建议为：先处理碰撞/致命危险，再处理超时，再判定成功，然后推进程序；若游戏需要不同顺序，必须显式覆盖此默认并提供理由。
- 到达目标后是否立刻结束程序，还是允许继续执行，必须明确。若继续会离开目标，应说明目标状态是否保持。
- 超时、指令上限、不可达、非法移动、提前停止等结果需区分状态并给出对应反馈，不能全部归为普通“没完成”。

## 5. 示例转移表：离散格网迷宫车

此表是定义方式示例，不要求所有游戏照搬全部积木：

| 指令/事件 | 前置条件 | 状态效果 | 控制流与判定 |
|---|---|---|---|
| `前进一步` | 执行状态为 `running` | 按当前朝向计算相邻格；可走时更新位置，遇墙/越界/陷阱按关卡规则处理 | 成功移动后先判危险/超时，再检查目标；未终止才进入下一条 |
| `左转一次` / `右转一次` | 执行状态为 `running` | 只改变朝向 90°，位置不变 | 检查是否有朝向类目标；未终止则进入下一条 |
| `设置速度 v` | `v` 在允许范围内 | 更新权威速度；之后的行驶时间按速度规则计算 | 有效时进入下一条；超限按明示规则拒绝、夹取或失败 |
| `等待绿灯` | 当前路段受信号灯控制 | 红灯时执行状态变为 `waiting`，位置不变；绿灯时恢复 `running` | 红灯时程序计数器停在此指令；绿灯后进入下一条；超时/取消按规则终止 |
| `如果前方有陷阱` | 条件块当前被执行 | 读取前方格状态，不移动 | 条件真进入 `then`，假进入 `else` 或跳过空分支；分支完成后回到容器后的下一条 |
| `停止` | 执行状态为 `running` | 执行状态变为 `stopped`，速度归零（若适用） | 不再取下一条；只有已满足明示的终点条件才算成功 |

本例只有在地图明确绘制格网并定义每格尺寸时才适用。“前进一步”此时表示恰好移动一格。

## 6. 示例转移表：无格网的连续车辆

假设地图单位为米、速度为米/秒，且本例采用恒速和以秒计的模拟时间：

| 指令/事件 | 前置条件 | 状态效果 | 控制流与判定 |
|---|---|---|---|
| `设置速度 v 米/秒` | `v` 在允许范围内 | 更新当前速度 | 有效后推进到下一条；超限按明示规则拒绝或失败 |
| `前进 t 秒` | 执行状态为 `running`，`t > 0` | 沿当前朝向计算 `d = v × t`，连续更新坐标；若提前碰撞，在首次接触位置停止 | 完整走完时长后再推进；碰撞、陷阱、目标或超时按明确优先级终止/继续 |
| `左转 θ°` / `右转 θ°` | 执行状态为 `running`，角度合法 | 原地改变方向 `θ`，不改变坐标 | 完成角度变化后检查方向目标，再推进 |
| `停止` | 执行状态为 `running` | 速度立即归零并停止程序 | 不再执行后续指令；依目标状态判定成功或提前停止 |

若游戏以 km/h 输入速度、以秒输入时间，则换算为 `距离(米) = 速度(km/h) ÷ 3.6 × 时间(秒)`。若采用不同换算或车辆转弯物理，必须在本项目规则中显式定义，不能沿用无格网“一步”的概念。

## 7. 验收状态机

- 为转移表中的每条指令至少走一条成功路径和一条适用的阻塞/失败/边界路径。
- 记录一条完整通关轨迹：每步的指令、执行前状态、执行后状态、程序计数器去向和用户可见结果；确认角色位置、朝向和程序高亮相符。
- 验证目标检查发生在规定时机，抵达目标不会多执行一条移动；陷阱/碰撞、绿灯等待、超时和停止不会错误地判成通关。
- 验证重置会把世界、执行状态、计时、等待条件和循环计数一起恢复；旧的异步步骤不得在重置后继续写状态。
- 验证显示计时、速度和进度均由权威状态派生，与模拟器实际规则相同。
- 对无格网地图记录速度、时间、坐标单位和位移公式，并核对实际执行结果；不能只检查积木标签或动画。
