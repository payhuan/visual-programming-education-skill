# 图形化编程积木系统规范

本规范用于自绘或自建的积木式指令界面。若用户指定 Scratch、Blockly 或项目已有的积木框架，优先遵循其官方/项目约定，并让游戏内的指令语义与之兼容；不要同时混用两套连接和造型规则。

## 1. 先确定最小积木粒度

在决定形状和绘制积木前，先按场景列出：

1. **状态**：角色/车辆当前位置、朝向、速度、收集物、机关/信号灯状态、剩余时间等本关确实会用到的数据。
2. **原子动作**：一次执行只完成一个基本动作，并有明确的状态变化，例如前进一步、左转一次、右转一次、停车/结束、设置速度、拾取物品。
3. **可检测条件**：只读取明确的场景状态，例如前方是否有墙/陷阱、信号灯是否为绿、目标是否到达。
4. **控制结构**：仅在学习目标需要时提供等待条件、如果/否则、重复等组合原子动作的结构。

按最小有意义操作设计积木：积木执行后应能单独说明“改变了哪个状态”或“检查了哪个条件”。不要把多个动作或条件打包成一个高层捷径来代替待学内容。例如，若学习目标是路径规划，“前进到下一站”不应代替“前进一步”；若目标包含转向决策，前进积木不应自动替学生转弯。只有用户明确要求高层命令，或关卡目标本身就是高层规划时，才添加这样的复合块，并清楚标明它隐藏了哪些动作。

迷宫/车辆类场景可从以下原子积木中按需选择，不能不加判断地全部塞进每关：

- `前进一步`：沿当前朝向移动一个格/一个明确路段；遇墙、越界或撞陷阱时按规则停止或触发结果。
- `左转一次`、`右转一次`：只改变朝向，不同时移动；转向角度由场景规则固定或作为参数明确显示。
- `停止`：结束当前程序或使车辆保持静止；不可与“等待”混为一谈。
- `设置速度`：只改变速度状态；若有上限（如 30），输入范围、超限处理和计时影响都须明确并真实执行。
- `等待条件`：暂停执行但不移动，直到明确条件满足或触发超时/取消行为；例如等待绿灯。不能显示“等待”但直接跳过红灯。
- `前方有障碍？`、`信号灯为绿？`等条件：只读当前场景状态，供条件块使用；陷阱、墙和红灯通常是场景对象/状态，不要错误地做成玩家主动执行的动作。

动作块与控制块要分层：前进/转向/停止/设置速度是原子语句；“如果前方有障碍”“重复若干次”“等待绿灯”是控制结构或条件。避免把“遇红灯后自动等绿再前进”做成一个不透明块，除非这正是用户要教的高层抽象。

## 2. 单一积木目录

在实现界面之前，为每种积木建立统一定义目录。每个定义至少记录：

- 稳定的 `id`、显示名称/标签模板和所属类别。
- 结构类型：事件帽、语句、终止语句、值、布尔值或容器。
- 输入槽及其类型：数字、文本、布尔值、值表达式或语句栈；需要参数时记录默认值、允许范围和校验方式。
- 可连接位置：是否接受前一条语句、是否可接下一条语句、是否只能作为程序入口。
- 容器允许的内部槽及内部内容类型；例如 `repeat.body`、`if.then`、`if.else`。
- 执行前提、执行操作及状态效果、程序计数器/控制流效果、无效输入/动作的处理方式；状态机细节遵循[状态转移规范](state-machine.md)。
- 类别色、矢量图标、标签和必要的辅助说明。

渲染器、连接校验器和程序执行器必须读取同一套定义与程序数据。不要分别在 UI、校验和运行代码里维护容易漂移的标签表、类型表和答案字符串。

## 3. 统一块类型与连接形状

一个项目只采用一套连接几何；以下是默认约定：

| 类型 | 轮廓与连接 | 用途 |
|---|---|---|
| 事件帽 `event` | 顶部为帽形圆弧；无上方连接口；底部有语句连接舌 | 程序入口。只能放在根级，不能插入语句栈或容器内部 |
| 语句 `statement` | 顶部有凹槽、底部有凸舌 | 可顺序连接的动作，如前进、等待、讲解 |
| 终止语句 `terminal` | 顶部有凹槽，底部平口且无下一条连接 | 明确结束所在语句栈的控制指令 |
| 值 `reporter` | 圆角胶囊形输出；匹配同类型的值槽 | 数字、文本或其他可计算结果 |
| 布尔值 `boolean` | 六边形输出；匹配布尔条件槽 | 真/假条件，如“前方有障碍？” |
| 控制容器 `container` | 语句形头部加 C 形/凹入式内部语句区；仍可接前后语句 | 循环、条件等拥有内部语句栈的语句 |

容器是语句的一种结构类型，不是任意背景框。其标题/参数区、内部语句槽和外部前后连接需在视觉上区分。块的类型由形状和连接共同表达，不能只靠颜色区别。

## 4. 输入槽和嵌套规则

- 数值、文本等可直接编辑的参数显示为带类型提示的内嵌字段/插槽；可拖入的值积木显示在相同类型的插槽中。插槽不得与语句连接口混淆。
- 值块只能接入兼容类型的值槽；布尔块只能接入条件槽；语句块只能进入根语句栈或声明可接收语句的容器槽；事件帽只能作为程序入口。无效连接必须被拒绝并给出视觉提示。
- 循环、条件等块将内部程序保存在命名语句槽中，例如 `循环体`、`如果` 和 `否则`。内部语句垂直堆叠并缩进，明确显示容器边界；子块可继续嵌套容器，前提是该槽允许语句。
- `if/else` 必须把两个分支显示为独立、带标签的区域，中间有清晰分隔。单分支条件不应伪装成有第二分支。
- 容器高度随内容自然增长；不得裁切、遮挡或把内部块绘制到容器之外。空槽显示虚线/浅色占位区和类型或用途提示；默认值块若只是占位，应与学生实际加入的块视觉区分。
- 嵌套结构必须存在于程序 AST/等价树形数据中，不能只通过缩进 CSS 或把标签拼成一行来模拟。拖入、删除、重排或嵌套后，画面顺序与执行顺序必须一致。

## 5. 贴图、图标和视觉语言

- 积木主体优先使用 CSS/SVG 矢量形状绘制，保证缩放、不同屏幕密度、长标签和嵌套时边缘清晰。不要用截图、整块位图背景或纹理图来模拟连接轮廓。
- 图标使用项目现有图标系统；没有时使用同一套简洁 SVG 图标，统一画布、线宽、填充和对齐。图标只辅助识别动作，不承载唯一指令含义；必须配有文字标签或可访问名称。
- 类别使用固定色板，并保持全项目一致；颜色用于辅助分类，不能代替块形、文字、插槽标签或连接提示。确保文字与底色有足够对比。
- 标签、参数字段、插槽和连接口按一致的间距、圆角、描边和字号规则排版。长文本应换行或扩大块，不得覆盖连接口、图标或参数。
- 允许使用主题装饰，但装饰不得降低可读性、遮盖结构边界或让同类块在不同页面呈现出不同语法。

## 6. 交互和响应布局

- 工具箱中的积木必须可拖入工作区；工作区中的积木必须可拖动到其他语句位置重排，或放入/移出其类型允许的嵌套槽。只支持点击“添加”再点击上下箭头，不满足拖拽要求；点击添加只能作为键盘/触控辅助。
- 拖动工具箱积木时创建一个新程序块，工具箱原块保留；拖动工作区积木时移动原节点。拖动容器块时，必须连同整个嵌套子树一起移动，不能拆散或丢失内部程序。
- 拖动过程中显示插入线、插槽高亮或其他明确的有效落点；无效类型或非法位置应拒绝放置并恢复原位置。有效的嵌套槽、值槽和程序栈需分别可识别。
- 拖放结束后，程序树、屏幕顺序、显示编号和执行顺序必须同步更新。拖拽不能导致重复节点、丢失节点或隐藏的旧指令继续执行。
- 拖拽应支持目标设备的指针/鼠标与触控；也要提供键盘可达的替代操作。不能以键盘替代为由省略实际拖放。
- 移动或删除积木时不得静默丢失子块；若操作会删除整段嵌套程序，应有清楚提示或可撤销机制。
- 小屏幕上程序工作区可以滚动或平移，但单块文字和内部插槽仍可读、可操作；不能让深层嵌套把工作区挤到不可用。
- 运行时高亮当前执行块；若当前执行在容器内部，应能看出所属分支/循环以及下一步位置。

## 7. 交付前校验

- 为每种积木检查：标签正常、图标齐全、连接类型正确、输入值能编辑或插接、执行操作已定义。
- 对照学习目标检查积木粒度：移动、转向、停止、速度和等待/条件等有意义的基本操作没有被高层捷径吞并；每块单独执行的状态变化可观察。
- 为每种容器分别检查空槽、单个子块、多子块、嵌套容器、条件双分支和长标签；确认容器扩展而不裁切，所有连接仍可操作。
- 用有效和无效类型组合检查连接规则；事件帽、语句栈、值槽、布尔槽和容器内部槽均按目录约定接受/拒绝。
- 执行一段含顺序、参数、嵌套和多分支的程序，确认 AST、屏幕显示、当前执行高亮和游戏状态变化一致。
- 在目标屏幕尺寸检查放大/缩放、文字溢出、滚动、触控命中区域和键盘可达性。
- 实际完成从工具箱拖入、程序内重排、拖入和移出嵌套槽；确认每种操作后的程序树与执行结果一致。
- 拖动容器时验证子树保持完整；尝试非法投放时验证块回到原位置且程序未改变。
